| 输入 | 路径 | 角色 |

规范正文是**渲染代码**：正文由 `dp.h2("1.9  …")`、`dp.p("…")`、`dp.codeblock(dp.src([...]))`、`dp.tbl(...)` 组成。
读规范时注意：`dp.src([...])` 里的行是**代码示例**，`dp.p("…")` 是散文说明（常含规则陈述）。
源码里 `lb()`/`rb()` 是左右花括号的字符串形态、`+ lb() +` 是拼接——读的时候还原成 `{`、`}`。

## 3. 状态定义（只能用这四个值）

| 状态 | 判据 |
| --- | --- |
| `已实现` | 语法被接受，且语义/代码生成齐备；实测样例编译通过（必要时可运行） |
| `部分实现` | 只有部分形态可用：例如语法接受但语义拦截、仅解释器支持而 LLVM 后端缺失、仅某一种子形态可用、或仅解析不接受 |
| `未实现` | 找不到任何实现痕迹，实测以语法/语义错误拒绝 |
| `非规范条目` | 该节属于设计立场/工程约定/文档说明，不含可编译的语言特性，无实现状态可言 |

**注意区分「规范写了但实现没有」与「实现有但规范没写」**：前者记 `未实现` 或 `部分实现`，后者要在「规范缺口」列里单独标记。

## 4. 证据要求（每条至少一项）

| 等级 | 形式 | 要求 |
| --- | --- | --- |
| A | 实测 | 写明样例文件、编译命令、结果（成功 / 错误码如 `E00035` + 原文） |
| B | 源码 | `文件:行` 形式，指出实现所在函数 |
| ~~C~~ | ~~记录~~ | **不作为证据**，见 §4.1 |

* 判 `已实现` 需 A 或 B；判 `未实现` **必须有 A**（实测报错），只凭「没搜到」不足以判定。
* 判 `部分实现` 必须说明缺的是哪一半。

### 4.1 记录不可信，必须实测（用户 2026-09-27 明确指令）

`ROAD.md`（含其 `[x]` / `[~]` / `[ ]` 标记）与 `CHANGELOG.md` **一律不可作为判定依据**，
只能当**待验证的线索**，用来提示「这里可能有东西可查」。理由：标记会漂移——`[x]` 可能
实际只落了语法层、或只落了其中一种子形态、或后续被改坏、或记录写在设计意图阶段。
反向亦然：`[ ]` 可能早已被顺手实现而未回填。

因此：

* 凡记录声称「已落地」的条目，**必须实测或查源码复核**；复核不过，按实测结论记状态。
* 凡记录声称「未落地」的条目，若实测可通过，按实测结论记状态。
* 记录与实测不符时，在「备注」列写明：`记录不实：ROAD.md 第 N 行标 [x]，实测 <结果>`。
* 记录里的 commit sha 只能用来定位代码，不能代替验证。

### 4.2 发现记录不实，要改正记录

实测确认记录不实后，**直接改正**记录文件（这是本次任务授权范围内的写入，
与「不得改语法规范」不冲突——规范指 `tofflib/spec/`）：

* 改 `F:/Projects/tie-repo/tie-main/ROAD.md` 对应行：修正 `[x]`/`[~]`/`[ ]` 标记，
  并在该行末追加一段 `**记录更正 <日期>**：<原记录怎么说> → <实测是什么>（证据：<样例/命令>）`。
* **只改实测确证的部分**。有一分证据改一分记录，不要顺手重写整段。
* 拿不准的（例如实测失败但怀疑是自己样例写法有误）**不要改记录**，只在报告里记为
  `待复核`，并写清可疑点——改错记录比不改更糟。
* 每次改动都记进产出文件的 `## 记录更正` 小节（原行号、原标记、新标记、证据），
  便于主代理汇总与用户复核。

**判定「实现没有」之前先排除自己写法有误**：规范示例是散文式示意，未必逐字可编译。
先查编译器自身源码里的同类写法（编译器是 tie 写的，它的用法一定合法），
再下结论。做法示例：`grep -n "actor " compiler/frontend/*.tie`。

**「grep 不到」不等于「不存在」**：两种已发生的误判模式，务必避免——

1. **grep 范围过窄**：库函数不在编译器源码目录里，而在库根 `tlib/std/`（`$TIE_LIB_ROOT`、
   `~/.tiec-lib/tlib`）。实例：`trim` 判「不存在」，实际由 **p.9.13.2 隐式前置**
   （`compiler/driver/prelude.tie`）暴露——logic/script 角色的文件会自动获得
   `import "/std/prelude.tie" as lang` + `using lang;`，于是 `trim`/`to_lower`/`map_has`
   等 16 个裸名可用。判「某函数不存在」前先试 `grep -rn "func <名>" <库根>/std/`。
2. **照抄规范示例导致误判**：规范示例本身可能引用不存在的 API。实例：`map_new()` 与
   `age.has(...)` 在实现里都**不存在**，我据此误判「映射能力缺失」——实际映射
   （字面量创建、`map_has` 判键、`a + b` 合并、`a with { }` 更新）全部可用。
   **正确做法：先用实现能接受的写法建立正例，再判规范示例是「写法不同」还是「特性缺失」。**
   两者结论完全不同：前者是规范缺口，后者才是未实现。

## 5. 实测方法

```sh
# 目录：F:/Projects/tie-repo/tiec/_spec_audit/<字母>/
# 文件名：s<节号>.tie，例如 2.15 节 → s2_15.tie
# 必须加 --no-cache：编译器有产物缓存，源码改动后旧缓存会导致误判
/f/Projects/tie-repo/tiec/compiler/tiec.exe --no-cache s2_15.tie -o s2_15.exe 2>&1 | tail -3
```

* 样例要**最小**：只写该条目需要的那几行，外加 `type tie<logic>` 头与一个 `func main() -> i64 { return 0 }`。
* 报错输出可能是 GBK 乱码（终端编码问题），但 `error[Exxxxx]` 码是可靠的——用错误码判定。
* 想确认「能编译」之后「行为正确」，可再加 `-o` 后直接运行 exe（`./s2_15.exe`），比对 stdout。
* 批量：把多个样例合成一个 .tie 一次编译，可显著省时间；但一个失败会掩盖后面的，**建议一条一条编译**，或分组后二分定位。

## 6. 输出格式（严格照抄，不要加小节标题以外的内容）

产出写到 `F:/Projects/tie-repo/tiec/_spec_audit/out/<你的字母>.md`，UTF-8，形如：

```markdown
## 第 N 章  章名

| 节 | 条目（规范要求） | 状态 | 证据 | 备注 |
| --- | --- | --- | --- | --- |
| 1.9 | 插值字符串 h"...{e}..." | 已实现 | A: s1_9.exe 通过；B: lex_scan.tie:556 | — |
| 2.16 | 精确数值类型 d 后缀 | 未实现 | A: E00000 无法以 TokenX 开始表达式 | 规范 §2.16 有完整定义 |
```

* 表格每行只描述**一个可判定的条目**；一节若有多个并列特性（如 1.9 有四种字符串形态），拆成多行。
* 「条目」列用规范自己的话，简短（≤ 30 字），不要复述整段。
* 「备注」列写：缺哪一半、规范与实现的不一致、记录不实的原委；没有就写 `—`。
* 章末追加一行统计：`> 本章：已实现 x / 部分实现 y / 未实现 z / 非规范条目 w`。
* 最后追加两节：
  * `## 记录更正` —— 每条：`ROAD.md 第 N 行 | 原标记 [x] → 新标记 [~] | 原记录说法 → 实测结论 | 证据`；
    已改的写「已改」，仅怀疑未确证的写「待复核（原因）」。
  * `## 本路结论` —— 3–8 条要点：最严重的未实现项、规范与实现冲突、值得上报的规范缺口。

## 7. 纪律

* 宁可标 `部分实现` 并写清缺什么，也不要含糊地标 `已实现`。
* 拿不准就实测。实测是最便宜的确证手段。
* 不要为了凑数把设计立场段落当成「未实现」——那是 `非规范条目`。
* 不要写「可能」「大概」；要么给证据，要么实测。
* **记录只当线索**：`ROAD.md` 的 `[x]` 不等于已实现，`[ ]` 不等于未实现，一律实测核对（§4.1）。
* **确认记录不实就改记录**（§4.2），只改有证据的部分；怀疑但未确证的记 `待复核`，不动文件。
