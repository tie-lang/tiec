## 本路结论

1. **【严重】zd v3 整层缺失（footer / 段表 / 列式编码族 / schema 演进 / 标准类型 / 图容器 六项全为「未实现」）。**
   规范 17.2 以「v3 把随机访问标准化为文件尾索引 footer」为一大节（含 25 字节 ZD3FT、段类型 0-6、四件编码族、schema_id 指纹、三态字段、timestamp/decimal/uuid、图容器），
   而 `tdb/src` 与 `tiec/compiler` 全仓无 `ZD3FT` 字样、无编码声明字段、无任何 v3 标记。这是本章最大的规范-实现落差，且 17.2 的读取义务明写「v3 实现须读 v2 与 v3」。

2. **【严重】两处「标记号已被占死」的硬冲突，落地 v3 前必须先重排号段。**
   （a）规范 17.2 规定 char/trit/code **一律走 ext 0xd7 子类型**，实现却把 char 编为 `0xC4`、trit 编为 `0xC5`（`tdb/src/zd.tie:400,411`），核心类型空间与规范不符；
   （b）`zd_ext.tie:62` 已把 **ext 标记 1/2/3 分给 char/trit/code**，而规范 17.2 把 **1/2/3 分给 timestamp/decimal/uuid**——撞号且规范自诩「不与 v2 既有标记碰撞」，事实相反。

3. **【中】17.3「三形态」与 `tink pipe` 全线未实现，帧协议本体反而很扎实。**
   帧层（长度前缀 + zd + CRC，CRC 失败拒帧）在 `std/tink.tie`、`std/tink_v2.tie`、`tdb/src/zd_stream.tie`、`tshell/src/srv.tie` 四处独立成立且实测通过；
   但**主形态「管道编排器」**、hub、库式互联层、`tink pipe` 命令、段级失败诊断全部缺失。规范把主形态写成默认形态，实现侧只有「节点」没有「编排」。

4. **【中】17.4 位长参数与规范区间不一致：规范 `n ∈ 2..144`，实现只认 17 个离散档位。**
   实测 n=2/48/69/92/144 有输出，n=5/7/100 返回空串（`tsha1.tie:18` 枚举集合）。代表档位与四模型参数（R=12/14/16/8）本身完全达标。

5. **【中】17.1 头部扫描规则与规范示例互相打架（规范缺口，非实现缺陷）。**
   规范 17.1 的示例把 `// pack.data.tie —— type tie<data>` 注释放首行且**不写声明行**；而 `scan_header` 遇首个非空行即终止头部区，
   于是 `.data.tie` 文件被文件名判为 `data`、头部默认 `logic`，触发 `error[E00000]`。正例须把 `type tie<data>` 置于首个非空行（`--compress-data` 因短路早于头部检查而不受影响）。

6. **【轻】17.2 内容哈希段算法不符 + 规范内部「9 vs 10 字节」自相矛盾。**
   规范要求内容哈希段用 **tsha1 族**，`zd_ext.tie:243 content_hash` 用 **FNV-1a 64**（功能齐全但算法不同）；
   规范头部定 10 字节、识别规则却写「9 字节…按 version 判定」，实现要求 ≥10（v3 头可识别为 version=3 但无 v3 语义）。
