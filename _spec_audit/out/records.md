## 本路结论

1. **整体可信度高，且失真方向单一。** 已核验的 74 条「属实」中，**没有一条**是「标 `[x]` 而实测失败」——凡记录声称已落地的语言特性（p.8 全 19 项、p.9.11 全 34 项、p.9.12 全 7 项、p.9.13 语言项），实测**全部通过**，且带出的 commit sha 经 `git log` 逐条验证**全部真实存在且提交信息与记录内容吻合**。这类记录的可信度相当高。

2. **最集中的失真模式：反方向的「已落地却标 `[ ]`」。** 4 条确证不实全部属此类：p.9.13.4（正文写「部分落地」标 `[ ]`）、p.9.13.5（双标记 `[ ] [~]`）、p.9.17.3（正文写「前半落地」标 `[ ]`）、p.9.20.3（正文写「已落地 b8a77f7」标 `[ ]`）。根因是**「标记」与「正文」由不同轮次写入、未回填同步**——正文如实记录了落地过程，行首标记停在旧值。

3. **次生的记录缺陷：同一条内自相矛盾。** p.9.13.4 的子条（第 417 行）称 `f = t -> expr` 未落地，而同一文件第 368 行（p.9.11.34）称「赋值位 `f = t -> expr` 已实现」；实测支持第 368 行。同一条/同一文件对同一能力给出相反结论，是最容易误导下游的一类失真。

4. **`[ ]` 的「反向核验」很有价值：确有多项被顺手实现而未回填。** p.9.10.11（tlib `std/big.tie` 536 行，头注直接引用该 ROAD 编号）、p.9.10.12（tlib `std/radix.tie` 111 行）两处属「模块已入库但记录仍标未落地」——虽因探针编译失败（E00590）或未达设计完整形态而未能判为「确证不实」，但已说明 `[ ]` 与仓库真实状态存在落差。

5. **`[ ]` 项的反向证书也证明记录未「谎报完成」：** p.8.3.1（actor 字段初值被静默忽略，实测返回 0）、p.8.3.2（async 返回值报 E00178）、p.9.11.24（默认值仍限字面量，E00359）、p.9.11.27、p.9.11.35（atomic 仍需 unsafe，E00376）、p.9.1.4–7、p.9.7.2、p.9.22 整块——**均确未落地**，标记无误。

6. **建议的记录维护纪律**（供主代理写入规范或纪律段）：
   * **标记与正文同写**：正文若出现「部分/前半/已落地/待补」等词，行首标记必须同批同步，禁止分轮次各写一半。
   * **禁止双标记**：`- [ ] [~] …` 这类并列标记一律非法（本次发现 1 处）。
   * **落地即回填**：某能力若由**后置**工作（如 p.9.21.5 的 pub const 护栏、p.9.11.26 的 ref/move 约定）改变了旧探针的成败，须同步更新旧探针或加注，否则「X/Y PASS」类断言会静默失效（p.9.12.4 即此情形）。
   * **以实测与 commit 双证**：本路证明 commit sha 是廉价且可靠的「记录自证」手段——凡记录带 sha 者应定期 `git log -1 <sha>` 抽验；不带 sha 的条目（如 p.9.0.x 仅链路到「未建仓」）应补锚点。
