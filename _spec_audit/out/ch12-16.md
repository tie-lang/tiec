## 发现的实现缺陷（编译器 bug，非「未实现」）

### #1 `#cfg` 条件求值不 trim 键 ⇒ 规范写法静默为假（高危）

* **最小复现**（`z/t1.tie`，Windows 主机）：

  ```tie
  type tie<logic>
  #cfg(os = windows)
  func f() -> i64 { return 1 }
  #end
  #cfg(os = linux)
  func g() -> i64 { return 2 }
  #end
  func main() -> i64 { println(to_string(f())) return 0 }
  ```
  编译命令：`./compiler/tiec.exe _spec_audit/z/t1.tie --no-cache --target windows-x64 -o F:/Projects/_tmp/t1.exe`
  结果：**`error[E00489] @5:20: 未定义的函数 'f'`** —— 即 `os = windows` 这条**在Windows 主机上
  带 `--target windows-x64` 仍被判为假**，正确分支被裁掉，且**无任何诊断提示条件为假**。
  把源码改成 `#cfg(os=windows)`（去空格）后 rc=0、输出 `1`（对照 `z/t3.tie`）。

* **根因**（B: `compiler/frontend/cfg_preproc.tie:162-168`）：`eval_cond` 拆分 `键=值` 后
  **只对 `val` 调用 `cp_trim`**，`key` 直接 `cp_slice(c, 0, eq)` 未 trim ⇒ `key == "os "`
  落进 `else { r = false }`（同文件 :195-196 「未知键 = 假」）。
  值侧有 trim：`val = cp_trim(cp_slice(c, eq + 1, len(c)))`（:162）。

* **影响面**：规范 §12.8 与 §16.12 给出的**唯一**示例形态就是带空格的 `#cfg(os = linux)`；
  按规范书写的条件编译在 tiec 上**静默失效**（选错分支），且用户拿不到任何提示。
  `debug`/`release` 裸键不受影响（无 `=` ⇒ 不走拆分分支），故现有用例未暴露此缺陷。

### #2 `n %%= 2` 破坏后续语句解析（编译器 bug，非特性缺失）

* **最小复现**（`z/bug_pctpair.tie`）：

  ```tie
  type tie<logic>
  func main() -> i64 {
      var n: i64 = 7
      n %%= 2
      println(to_string(n))
      return 0
  }
  ```
  结果：**`error[E00832] @7:9: 无法以 Eq 开始表达式。`**
  报错位置（文件末尾 `}` 之后）**与真正的错误源（第 5 行 `n %%= 2`）无关**，
  诊断坐标因此完全误导。若删掉紧随其后的 `println` 一行则 rc=0 ——
  即「`%%=` 之后的第一条语句被吞掉」，错误坐标落在下一条语句上。

* **对照**（`z/ctrl_intdiv.tie`）：`n \= 2`（整除复合赋值）完全正常，rc=0、输出 `3`。
  说明这是 `%%`/`%%=` 记号族特有的问题，不是复合赋值通用问题。

* **根因定位**：`lex_symtab.tie:100` 的符号表有 `"%%"`（tag 111）与 `"%="`（tag 65），
  **无 `"%%="`** ⇒ `%%=` 被切成 `%%` + `=` 两个记号，`n %% = 2` 走的是「表达式语句
  `n %% (=2)`」的解析路径，其后残留状态污染下一条语句。
  这解释了 ch16 §16.4/§16.10 的 `n %%= 1 // 原地取余并写回` 为何不可用（记为**未实现**），
  同时也解释了这条**额外的解析器缺陷**（记为**编译器 bug**）。

* **注意排除误判**：本条曾一度被我误读为「`->` 管道与 `%%=` 交互」——
  进一步最小化（`z/b13.tie`）显示真正的触发条件是 `%%=` 本身，
  而 `var q = t -> 1` 之所以失败是另一回事（`E00547 箭头目标必须是函数、调用或可赋值变量`
  —— `-> 1` 本就不是合法管道目标，属**我的写法错误**，非缺陷）。已按§4.2「拿不准不要下结论」
  处理，撤回该误判。

### #3 `code` 值存入运行期变量未被前端拦截（延迟到 LLVM 才崩）

* **复现**（`z/p12_1b_codevar.tie`）：`func stash(x: code) -> i64 { var v = x return 0 }`

## 本路结论

1. **ch12/ch13 两章零未实现**。宏（元编程）落地程度高：函数式宏、模板宏、准引用/插值、
   卫生、跨文件 `pub macro`、注解、条件编译裁剪全部可用。移动语义四约定齐备，
   `E00372` 已移动检出实测生效，门控分层（凭据始终检查 / 堆类型 `TIE_MOVE_CHECK` 默认开）如规范所述。

2. **最严重的规范 × 实现冲突：ch13 §13.1「默认按值 = 独立值」与实测相反**。
   `table`/`map` 是浅拷贝共享句柄（`z/p13_1c_share.tie`、`z/p13_cow.tie`）。
   规范的「独立」只能理解为「无需显式 move」，字面表述需修订；
   且`ROAD.md:520` 的「容器维持拷贝」表述同样与实测不符。**用户已提示的
   `fn-capture-whitelist.md` §1「值语义」问题在此得到第二次实测确认。**

3. **ch14 整章未实现（8 条）**，且是**规范定稿但实现未开始**，不是实现掉队：
   所需新关键词 `view`/`component`/`style`/`theme`/`action`/`Slot`/`@元素块` 在关键字表中全部不存在；
   `@` 已被注解语法占用（`E00453悬空注解`）。唯一已实现的是 `type tie<ui>` 文件头可识别
   （角色已注册、输出管线为 `pass`）。渲染/控件运行时属**独立仓 `tie-lang/tiu`**
   （其渲染引擎设计文档自述「本期只落到设计，不进入实现」）。
   另注：规范 §14.5 的图语法记法（`graph P { node a … }`）与实现侧设计稿
   `tie-primitive-op-design.md` §5 的记法（`{ A } - { B -> ~ A }`）**已经脱节**，需先统一再落地。

4. **两个真实编译器 bug**（均已给最小复现）：
   ① **`#cfg` 键不 trim** ⇒ 规范唯一示例形态 `#cfg(os = linux)` 静默判假、选错分支、
      **无任何诊断**；这是本轮最隐蔽也最容易在用户代码里造成错误的缺陷。
   ② **`n %%= 2` 吞掉紧随其后的语句**，错误坐标落在下一条语句上（`z/bug_pctpair.tie`）；
      根因是符号表缺 `%%=`（只有 `%%` 与 `%=`），`%%=` 被切成两记号后走偏解析路径。
      `n \= 2` 正常，说明非复合赋值通用问题。

5. **ch15 是「工具链外壳」而非语言特性**：真正缺失的只有 `--check` 与 `--emit-pdf` 两个
   规范明列的开关（均报 `E00887`，且与「未知开关」不可区分）；格式化/静态检查/REPL/LSP
   四项能力都**已实现但在兄弟仓库**（`tsp`、`tshell`、`vscode-tie`），且**没有
   `tiefmt`/`tielint` 这样的独立命令名**——属规范与工具链组织方式的不一致，不算 tiec 缺口。

6. **ch16 速查表整体可用（7 已实现 / 6 部分实现 / 0 未实现）**，但作为「速查」它与实现有多处
   **写法不符**（不是能力缺失）：enum 载荷须位置式 `Circle(i64)` 而非 `B(x: i64)`；
   容器/字符串方法形态 `t.sort()`、`s.trim()` 全被拒（须用自由函数）；
   `with {k: v}` 只作用于记录表；`async` 只能出现在 `actor` 内；
   `t <- v` 追加被拒（须 `table_push`）；命名实参只能跳过**有默认值**的形参，
   故 §16.3 的 `f(a: 1, c: 3)` 示例签名本身不成立；
   顶层 `extern func` 被拒。**ch16 作为读者的「速查表」，其示例代码的可编译性明显落后于实现**
   —— 这是本轮值得上报的规范缺口。

7. **待复核项**（证据不足，未判状态）：
   * 格式化输出的确定性（无 `tiefmt` CLI可跑两次对比）；
   * 文档注释的 `#` 小标题层级与 `-` 清单两种构件；
   * 语言服务「按文件增量重算」的性能主张（tsp 有冒烟脚本但无增量证据）；
   * §15.4静态检查的四项中「恒真条件」「可简化成管道表达式的嵌套调用」两条无对应实现痕迹。
