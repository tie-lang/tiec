## 发现的实现缺陷（编译器 bug，非「未实现」）

### 缺陷 #1：`char` 参与运算/索引时 LLVM 类型错配（i32 vs i64）

* **症状**：任何把 `char` 值送进「需要真值类型」的位置的表达式，opt 报类型不匹配。
* **最小复现**（`_spec_audit/x/bug_char_c.tie`）：
  ```tie
  type tie<logic>
  func main() -> i64 {
      var t: table<char> = ['a']
      println(to_i64(t[0]))
      return 0
  }
  ```
  → `D:\LLVM\bin\opt.exe: '%8' defined with type 'i32' but expected 'i64'`（`E00883 中间优化失败`）
* **其他变体**：`bug_char_b.tie`（`var c = t[0]` 后赋值）→ `'%9' defined with type 'i32' but expected 'i64'`；`bug_char_a.tie`（`func f(s: string) -> char { return s[0] }`）→ `value doesn't match function result type 'i32'`；`s1_3.tie`（`var c: char = s[0]`，s 为 string）→ 同一 opt 错误。
* **根因**：`char` 在类型系统里是 `TK_CHAR`，`backend/llvmgen_str.tie:74-76` 映射为 LLVM **`i32`**；而表元素槽与 `trunc` 路径按 **`i8`** 或 **`i64`** 处理。具体：
  * `backend/irgen_stmt_p1.tie:181-201`（`tig_index_read`）的 `suffix`/`ret_ty` 分派里**没有 TK_CHAR 分支**——`bridge_suffix`（`irgen_p1.tie:180-192`）只认 string/bool/f64，char 落到 `"i64"` 兜底；
  * `backend/irgen_str_p2.tie:145-160`（`s21_table_at_ex`）按 `elem_llvm_ty` 建结果槽，char 传入的是 i64 语义；
  * 但字面量侧 `backend/irgen_lit.tie:96` 确实发 `const_i i32`，于是 store 端 i32、load 端 i64。
  * 另有一条相关不一致：`backend/irgen_agg_p1.tie:615` 注释明写「bool/char 槽存 i64，从 i64 槽 load 后 trunc 还原 i1/i32」，说明**聚合槽按 i64 存、标量表达式按 i32 算**这条分裂只在一处补了 trunc（`irgen_agg_p1.tie:707-708`），下标读路径没补。
* **建议修法**：①在 `tig_index_read` 的 `ret_ty` 分派里为 `TK_CHAR` 增设 `ret_ty = types.named(TK_CHAR)`（使结果槽为 i32，与字面量一致），或在 `bridge_suffix` 前把 char 归一为 i8 并同步 `s21_table_at_ex` 的槽型；②更稳妥的做法是让 `char` 在值表示上统一走 i32（LLVM `i32` 已是 `llvm_ty` 的既有映射），在**所有**跨越「i64 聚合槽 ↔ i32 标量值」的边界统一插 `zext/trunc`——即把 `irgen_agg_p1.tie:615` 注释描述的约定推广到 `tig_index_read` 与 `s21_table_at_ex`。建议先加回归探针：`table<char>` 读、函数返回 char、string 下标赋给 char 三条。

### 缺陷 #2：宽类型（num/text/misc）变量在任意使用点生成 `sext … ptr`

* **症状**：`var a: num = 42` 能编译，但**只要读一次**（打印、传参、运算）就崩。
* **最小复现**（`_spec_audit/x/w_num1.tie`）：
  ```tie
  type tie<logic>
  func main() -> i64 {
      var a: num = 42
      println(to_string(a))
      return 0
  }
  ```
  → `opt.exe: '%5' defined with type 'i64' but expected 'ptr'`
  同族：`w_misc.tie`（`var m: misc = true; println(to_string(m))`）→ `'%5' defined with type 'i1' but expected 'ptr'`；`w_misc3.tie`（`take_misc(true)`，形参 `x: misc`）→ `'%0' defined with type 'i1' but expected 'ptr'`。
* **根因**：宽类型归约只做在**声明点**，没做在**使用点**。
  * `backend/irgen_stmt_gen_p1.tie:22-30`：var 声明时若标注是 `TK_NUM`/`TK_TEXT`/`TK_MISC`，就把槽型换成 `node_types[init]`（这解释了为什么 `var a: num = 42` 本身能过，槽是 i64）；
  * 但 `frontend` 从不把被声明变量的 `node_types` 归约（`grep -rn 'TK_NUM\|TK_TEXT\|TK_MISC' compiler/frontend/sinfer*.tie compiler/frontend/scheck*.tie` 只命中 `sinfer_ret_q2.tie:182` 一处、与本条无关）；
  * 于是使用点的 `node_types[标识符]` 仍是 `TK_NUM`(=16) / `TK_MISC`(=18)，`backend/llvmgen_str.tie:153` 的兜底 `return "ptr"` 生效；
  * `backend/llvmgen_inst_gen_p1.tie:542-546`（`gen_inst_b_19_sext`）按 `llvm_ty(源类型)` 印出 `sext ptr … to i64` —— **源类型被印成 ptr**，而操作数实际是 i64/i1 值。
  * 一句话：**归约发生在 alloca 处，没有传播到 slot 的类型视图**。
* **建议修法**：在 sinfer 的 var 声明处理里，当标注为宽类型时，把该名字的 `node_types` 就地改写为 `node_types[init]`（与 irgen 的归约同一处、同一结果），并给形参 `x: num/text/misc` 补同样的形参类型归约；这样 `llvm_ty` 不再落到 ptr 兜底，`sext` 源类型也就正确。同时建议在 `llvm_ty` 里为 `TK_NUM`/`TK_TEXT`/`TK_MISC` 加显式分支（返回 `"i64"`/`"ptr"`/报错），让漏归约处**编译期报错**而不是生成坏 IR——现在这类 bug 会伪装成 LLVM opt 的类型错，定位成本极高。

### 缺陷 #3：struct 字段声明为 `array<T, N>` 时生成的 LLVM 类型与初始值不匹配

* **症状**：`array` 作局部变量/顶层变量正常（s2_13b.tie、s1_13d.tie 均 rc=0），但**作 struct 字段**必崩。
* **最小复现**（`_spec_audit/x/s2_18d.tie`，注意**不含任何泛型**）：
  ```tie
  type tie<logic>
  struct Buf {
      var data: array<u8, 512> = [0, 0, 3]
  }
  func main() -> i64 {
      var b = Buf()
      println(to_string(len(b.data)))
      return 0
  }
  ```
  → `opt.exe: '%22' defined with type 'ptr' but expected '[512 x i8]'`
* **对照组**：把泛型值参数去掉（s2_18d）**同样失败**；把字段换成 `table` 或标量则正常。这说明 §2.18 的「值参数 + array 字段」失败并非泛型值参数的问题，而是「struct 字段是 array」这一形态整体坏掉。
* **根因推断**：字段槽按聚合类型 `[512 x i8]` 分配（`llvm_ty` 的 K_ARRAY 分支，`llvmgen_str.tie:76-81`），但字段初值 `[0,0,3]` 走的是表字面量路径（`irgen` N_TABLE_LIT → `s21_table_new` 返回 ptr 句柄）。**字段声明的聚合类型与初值的表句柄之间没有做 array 广播/转换**——局部变量路径上 `array_init(...)` 内建承担了这个转换（`sinfer_ret_q2.tie:173-183` + `irgen` 调用点按目标数组类型生成 `[N x T]` 填充），字段路径没接上。
* **建议修法**：在 struct 字段初始化的 irgen 分支上补 array 目标类型转换——与 `array_init` 调用点已有的「按目标数组类型生成全等值填充」逻辑复用同一段代码（提取为 `s21_array_broadcast(dst_addr, elem_ty, n, src)`），字段初值为表字面量且字段类型为 `K_ARRAY` 时调用它。先加回归探针：`struct{var a: array<i64,3>}` 配字面量初值与 `array_init` 初值各一条。

## 本路结论

1. **ch01 最实质的缺口是插值格式说明符**（§1.9）。`parse_interp_chain`（`frontend/pexpr_p1.tie:558-596`）的循环体只有 `parse_expr()` + `expect(lex_rbrace)`，规范用两个表格 + 5 行示例定义的 6 段规格（对齐/填充/符号/宽度/精度/类型）一段都没有。12 个规格探针全部报同一个 `E00484 期望 '}'，实际是 Colon`。这是「规范写得比实现细」的典型落差。
2. **ch02 有两处「整节级别」的缺失**：§2.16 精确数值类型（`0.1d` 十进制字面量、`div_ctx`/`half_even` 舍入上下文、无 `dec` 模块）与 §2.10/§3.16 的 `is` 类型判定（全仓零命中）。另外「容器方法形态」是 ch02/ch03 最大的系统性缺口：§2.19 的 9 个字符串方法、§2.20 的 6 个集合方法、§3.11 的 `t -> [0]` / `u -> .name` 全部不可用——能力都在库里（`string.tie` / `sort.tie` / `collection.tie`），只是**没有方法形态的桥**。实现对此有一道明确边界：`sinfer_q3.tie:549` 的 `E00475`「方法调用的对象必须是 struct/enum 实例」，即方法接收者**只支持 struct/enum**；`s.chars()` 是唯一例外（走独立的迭代器协议）。
3. **与现有文档状态表矛盾之处**（按要求单列）：
   * `backend/irgen_agg_p1.tie:615` 的注释声称「bool/char 槽存 i64，从 i64 槽 load 后 trunc 还原 i1/i32」是**通用约定**，但下标读路径（`tig_index_read`）没遵守 → 缺陷 #1。注释描述的约定覆盖面大于实际实现。
   * `backend/irgen_stmt_gen_p1.tie:19-30` 的注释把宽类型归约描述为「按 init 的实际推断类型定槽型」，读起来像是宽类型已被完整处理；但它只覆盖 alloca，使用点仍坏 → 缺陷 #2。**这条注释是本次审计里最容易误导人的一处**。
   * `frontend/pexpr_p4.tie:29` 的注释说块管道「到达本层时 `{` 只可能是块管道开头」，实测成立；但规范 §3.11 的跨行缩进示例不可用，注释未提这个限制。
4. **规范内部自相矛盾 3 处，实现都有明确立场**（建议上报规范修订）：
   * §5.1「返回类型不可省略」+ §5.12「返回类型必须显式标注」 vs §2.7/§2.14「返回类型可省略」——实现站在**可省**一侧（s5_1a.tie）。
   * §4.12「只能跳到同一块或**已经执行过的**外层块」 vs 其示例（从 `if` 块内 `goto #done` 跳到外层标签）——实现按 `scheck_p2.tie:213-221` 的 R2 强制「外层目标序号必须更小」，示例逐字不可编译（E00195）。
   * §2.7「模块内函数的参数与返回类型全省略」+ 示例 `func help(a, b) { return a + b }` vs 实现 `E00813 参数必须标注类型`——参数类型**必须**标注，无豁免。
5. **ch05 闭包/捕获/env 全部达标，是本次审计中状况最好的部分**。§5.10 的白名单禁令（E00697）、按值 vs 按引用的划分（标量/struct/array 快照、表/映射共享）都用**运行输出**验证过语义正确，不只是编译通过——这与 `tests/language/closure_agg_capture.tie` 记录的 env 布局修复（`malloc(8*ncap)` → `agg_ty_size`）是同一条线，近期改动没有引入回归。§5.13 隐式单参闭包是唯一缺口，且是被花括号消歧规则（记录字面量优先）挡住，属设计裁决冲突而非疏漏。
6. **ch04 是唯一零未实现项的章**（16 已实现 / 3 部分实现 / 0 未实现）。3 个「部分」都不是实现弱：goto 与跳转限制是**实现的限制比规范严格**（见结论 4）、`yield` 的生成器语义归 ch06 惰性求值分路、`panic` 归 ch08。§4.14 解构四位置（含 `...rest`）、§4.10 defer 逆序、§4.13 分支即表达式都是完整可用的。
7. **三个编译器缺陷（#1 char / #2 宽类型 / #3 struct 里的 array 字段）有共同特征**：都在 LLVM IR 类型化阶段暴露，且都因「某个 LLVM 类型映射只在部分路径被遵守」而发生。三者都会伪装成 `opt.exe` 的类型不匹配（E00883），而不是 tie 层的可读诊断——这是本次审计认为最值得优先修的：**给 `llvm_ty` 的兜底分支加显式错误**，让这类问题在 tie 编译期就暴露。
