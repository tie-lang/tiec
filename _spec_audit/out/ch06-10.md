## 发现的实现缺陷（编译器 bug，非「未实现」）

### #1 `println(struct)` 生成错类型 LLVM IR —后端必崩

* **症状**：任何 `struct` 值直接作为 `println` 实参，LLVM `opt` 阶段报类型不匹配，`E00883 中间优化失败`。**与是否定义 `to_string` 约定无关**。
* **最小复现**（`_spec_audit/y/bug_to_string3.tie`）：
  ```tie
  type tie<logic>
  struct V {
      var x: i64 = 1
  }
  func main() -> i64 {
      var v = V(1)
      println(v)      // 无任何 to_string 约定
      return 0
  }
  ```
  编译：`error[E00883]: 中间优化失败；opt.exe: '%5' defined with type '%struct.V = type { i64 }' but expected 'i64'`
* **对照**：`bug_to_string2.tie` 把 `println(v)` 换成 `println(v.to_string())` → **编译通过并正确打印 `V`**。说明缺陷只在 `println` 的「非字符串实参」路径上。
* **根因分析**：`println` 走内建变参路径（`compiler/frontend/sbuiltin_call_gen_q*.tie` → `compiler/backend/irgen_bi_*.tie`）。变参打包时把struct 实参按其 LLVM 结构体类型直接塞进 `i64` 形参槽，未做「非字符串实参的降级表示」（应走 `to_string` 约定或报类型错）。这解释了为何规范 §6.8 的 `to_string` 约定形态在`println` 上完全无法落地——**这条缺陷直接卡住 ch06 §6.8 的最后一行**。
* **建议修法**：在 `println` 的实参 lowering 处加一道guard——实参类型为 struct/enum 时，或（a）查找用户 `to_string` 约定并发射调用，或（b）报「类型不支持直接打印，请调用 `.to_string()`」。当前行为（生成坏 IR 交给 LLVM）是最坏的一种。
* **影响面**：ch06 §6.8（`to_string` 约定在`println` 上不可用）、任何想直接打印结构体的用户代码。语言自身的标准库若有任何 `println(struct)` 写法也会中招。

### #2 `to_i64(string)` 生成错类型 LLVM IR —后端必崩

* **症状**：`to_i64(<string 表达式>)` 恒定生成 `ptr` 类型的值，而消费点期望 `i64`。凡该值**不直接**作为 `i64` 返回/形参出现（即被存进局部变量后再用），必崩。
* **最小复现**（`_spec_audit/y/c12.tie`）：
  ```tie
  type tie<logic>
  func f(s: string) -> i64 {
      var n = to_i64(s)
      return 42          // n 不是返回值 → 崩
  }
  func main() -> i64 { return 0 }
  ```
  编译：`error[E00883]: 中间优化失败；'%3' defined with type 'ptr' but expected 'i64'`
* **为何之前没暴露**：`b7.tie` 把 `to_i64` 的结果直接 `return n`（`main` 声明为 `-> i64`）时**编译通过**——`b10.tie` / `b9.tie`同样通过。即该缺陷只在结果「落到局部槽再二次使用」时触发，掩盖面很大。
* **同族缺陷**（同样根型：`b8_to_f64.tie` / `b8_to_i32.tie`）：
  * `to_f64("7")` → `'%2' defined with type 'i64' but expected 'double'`
  * `to_i32("7")` → `'%4' defined with type 'i64' but expected 'i32'`
  * `to_u64("7")` → 通过（唯一正常的一个）
* **根因分析**：字符串在 LLVM 里是 `{ptr, len}`，`to_i64`/`to_f64`/`to_i32` 的实现（`compiler/backend/builtin_expr_seg1.tie:36-67` 识别，走 `compiler/backend/irgen_bi_*.tie` 发射）把「字符串→数值」这条**语义转换**当成了「取字符串的数值载荷」。正确实现应调用运行期转换例程（`strtol` 类）或走 `parse_int`（`compiler/frontend/sbuiltin_q1.tie:91` 把 `parse_int`/`parse_float` 归入 `builtin_call_b_to_string` 分支，是能用的那条路）。
* **建议修法**：`to_i64`/`to_f32`/`to_i32` 等对 **string 实参**改为发射到运行期转换函数（与 `parse_int` 同一路径）；对数值型实参保留现有 coercion 语义。
* **影响面**：§8.1/§8.2/§8.3 全部以 `parse_port(s) = Ok(to_i64(s))` 为范式的规范示例**都编译不过**（`bug_min4.tie` / `s8_2.tie` / `s8_1d.tie` 均命中）。改用 `parse_int` 后全部通过（`d1.tie` 编译运行正确输出 `port 8080` / `err empty`）——故这是**编译器缺陷，不是「?传播未实现」**。

### #3 `checked_div` 编译失败且无任何诊断输出

* **症状**：`checked_div(10, 0)` 编译 `rc=1`，但日志仅 45 字节且**不含任何 error 行**（`grep -E "error"` 零命中）。属「失败但无诊断」。
* **最小复现**（`_spec_audit/y/s8_5g.tie`）：
  ```tie
  type tie<logic>
  func main() -> i64 {
      var z: i64 = 0
      println(to_string(checked_div(10, z)))
      return 0
  }
  ```
* **对比**：`checked_add` 等同族是否同样静默失败未逐一验证；`compiler/backend/irgen_expr.tie:174-177` 把 `checked_add/sub/mul/div/shl/shr/neg` 整族都列在同一个分派里，疑似整族问题。
* **根因分析（未确证）**：疑似前端 `scheck` 未登记 `checked_div` 的返回类型，或后端该分派分支未发射值，导致 IR 生成中断而错误信息未落盘。**需进一步定位**（建议先看 `compiler/frontend/sbuiltin_q1.tie` 是否登记了 `checked_*` 族，再看 `compiler/backend/irgen_bi_*.tie` 对应分支）。
* **建议修法**：先确认 `checked_*` 族是否在 `sbuiltin_q1.tie` 登记表里；缺失则补登记。同时修「IR 生成失败必须落一条 error 诊断」这一诊断完整性问题——**编译失败却零诊断本身就是缺陷**。

### #4 `std/dataflow.tie` 无法编译 —share 域门禁挡死库自身

* **症状**：`import "/std/dataflow.tie"` 恒定编译失败：
  `error[E00899] @306:13: spawn 一个引用全局可变容器的闭包必须在 unsafe 块或 unsafe 函数中`
* **最小复现**（`_spec_audit/y/libtest.tie`，连调用都不需要）：
  ```tie
  type tie<logic>
  import "/std/dataflow.tie" as df
  func main() -> i64 { return 0 }
  ```
* **规避尝试全部无效**：`type tie<logic>` + `unsafe func main()` → 仍报；`type tie<logic, unsafe:share>` + `unsafe func main()` → **仍报**（见 `s10_9d.tie`）。
* **根因分析**：`std/dataflow.tie:305-313` 的 `run_par` 里：
  ```tie
  spawn(func() -> i64 {
      var nd = df_w_node[t]        // ← 引用模块级全局可变表
      var fv = df_fns[nd]
      df_slots[t] = fv(df_w_val[t])
      wg_done(wg)
      return 0
  })
  ```
  闭包捕获了模块级全局可变容器 `df_w_node`/`df_fns`/`df_slots`，被 `compiler/frontend/scheck_p2.tie:401-450` 的 share 域门禁判定为「引用全局可变容器的 spawn 闭包」，要求 unsafe 上下文 **+ share 域凭据**。
  关键点：`dataflow.tie` 头部是 `type tie<class>`（`tlib/std/dataflow.tie:1`），而 `scheck_p2.tie:425` 的 `g_spawn_unsafe[sp] == 0` 判定**只看函数/块级 unsafe 上下文，不看文件级 `type tie<..., unsafe:share>` 声明**——所以从调用方文件头加 `unsafe:share` 救不了库内部的 spawn。而 `~/.tiec-lib/tlib/std/dataflow.tie` 副本同样有此问题（`grep -c spawn` = 5，首行同为 `type tie<class>`），确认**不是副本不同步**。
* **建议修法**（二选一）：
  1. **库侧**（推荐）：`run_par` 的任务体不要直接捕获全局表。把本波快照（`df_w_node`/`df_fns`/`df_w_val`）与结果槽改成 `spawn` 前拷进局部变量再捕获；`df_slots` 在`spawn` 前建局部表、join 后回写全局。
  2. **门禁侧**：把文件级 `type tie<角色, unsafe:share>` 计入库文件内部的 `g_spawn_unsafe`（既然库作者已在文件头显式声明持有 share 域凭据，库内 spawn 就该被允许）。这同时是 §10.1「五域凭据 `share` 域挂载」的口径一致性问题——当前 `share` 凭据对**被编译的库自身**无效，只对调用方文件有效。
* **影响面**：`std/dataflow.tie` 是 ch10 §10.4/§10.9 唯一可运行的「数据流图」承载。库坏 ⇒ 规范 §10.4/§10.9 的替代路径也断了，故这两节只能判「未实现」而非「写法不同」。

### #5 表越界静默返回零值，与规范「检查不可关闭」相反

* **症状**：`xs[10]`（长度 3）不报任何诊断、不终止进程，静默返回 `0`；加 `--check-bounds` 也无效。
* **最小复现**（`_spec_audit/y/s8_5b.tie`）：
  ```tie
  type tie<logic>
  func main() -> i64 {
      var xs = [1, 2, 3]
      var i: i64 = 10
      println(to_string(xs[i]))    // 打印 0，退出码 0
      return 0
  }
  ```
  加 `--check-bounds` 重编（`s8_5e_cb.exe`）仍打印 `0`。
* **根因分析**：`compiler/backend/irgen.tie:120-121` `var g_check_bounds: bool = false` 默认关；更关键的是 `compiler/backend/irgen_agg_p1.tie:345` 注释明写「读越界→零值、写越界→**静默**」——越界裁决被硬编码为静默降级，`--check-bounds` 未改变这一裁决路径（`set_check_bounds` 存在但未接到该处）。
* **建议修法**：把越界裁决接到 `g_check_bounds`，并按规范 §8.5 把默认改为「开」；至少要在越界时发一条带位置的诊断。除零同理（`s8_5f.tie` 进程被 `SIGTERM` 终止，无消息无位置）。
* **说明**：这条同时是「实现与规范相反」的条目——规范写「这些检查**不可关闭**，因为它们的成本相对故障后果可以忽略」，实现是「可关闭且默认关、且关掉后完全静默」。静默返回零值比崩溃更危险（错误会传播到下游计算）。
* **与 ch11 审计的关系**：ch11 路已审过 `unsafe` 机制，但这条属**非 unsafe 路径的默认行为**，故在本路ch08 记为缺陷。

## 本路结论

1. **ch08 §8.4/§8.7 整章缺失**：`map_result`/`and_then`/`map_err`、`wrap_err`/`cause`/`root_cause` 全标准库零命中。规范 §8.7 的「错误链」是 ch08 里最大的一块空白，而它是错误处理章的核心叙事（逐层补充语境）。§8.4/§8.7 应视为规范单方面超前。**另两条未实现是内建检查**：§8.5 的越界静默返回零值、除零直接 `SIGTERM` 终止，均无位置信息，与规范「检查不可关闭、报告位置」相反（详见缺陷 #5，ch11 路未覆盖此路径）。ch08 之所以「已实现」仅 4 条，是五章里最低的。
2. **ch10 §10.4/§10.9 未实现且无替代**：任务图 `graph()`/`g.add`/`g.run()` 与图字面量 `{A} - {B}` 均无解析入口；唯一承载 `std/dataflow.tie` 因缺陷 #4 无法编译，故不能按「写法不同」降级为规范缺口。§10.7 `reentrant`、§10.6 `await` 连关键字都不存在（`lex_symtab.tie` 关键字表 69 项中无二者）。
3. **两处规范内部的自我矛盾（建议上报规范维护者）**：
   - §6.4 说「方法形态对内建类型同样适用」，但 §9.4 说内建「默认可见」——若方法形态普遍成立，§6.4 的示例 `s.len()` 就该能编译，实际不能。
   - §9.4 说 `iter_` 系是默认可见的内建，§6.11 又把 `iter_*` 定义为需要导入/适配的库函数。两者对同一批名字的可见性给出相反指示。
4. **三项「实现有但规范没写」的重要行为差异**（规范缺口，建议补写）：
   - `namespace <Struct>` 内**首参自动按引用**（`scollect.tie:344-370`）——规范的 `ref` 写法反被 `E00692` 拒。这不是能力缺失，是口径冲突，且导致 §6.10 遍历协议的「前进」语义写不回调用方。
   - actor 方法**必须 `pub`**（`E00177`）、actor **必须经 `run` 建立**（§10.2/§10.6 示例写法与实现不符）。
   - port 提升（§7.4）**必须在 unsafe 上下文 + 持 mem 域凭据**（`E00456`/`E00701`），规范 §7.4 未提此前置。
5. **`to_i64(string)` 后端缺陷（#2）污染了 ch08 三节的判定**：§8.1/§8.2/§8.3 的规范示例全部以 `Ok(to_i64(s))` 为范式，都因它编译失败。修这一处（或改用 `parse_int`），ch08 的示例即刻可跑——故这些条目判「已实现/部分实现」而非「未实现」。这是本路最值得优先修的编译器缺陷。
6. **§6.6 的常量性检查漏了普通 struct 字段**：`n6_6d4.tie`（`var x: i64 = g()`）编译通过并运行，而函数形参默认值有白名单校验（`scollect.tie:295-312`）、actor 字段也有（`scollect_port_q2.tie:181`）。同一约束三种对象两种待遇，属检查漏项而非设计选择。
7. **两处首轮误判已靠实测纠正**（记录在此以免后续重犯）：
   - §8.3 穷尽性检查：**已实现**（`E00014 switch 不穷尽……缺少 'Err'`）。首轮负例 `n8_3.tie` 误用裸名 `Err`，被 `E00489` 掩盖；改全名构造后立刻拿到真诊断。
   - §9.2 嵌套命名空间：**已实现**（`outer.inner.g()` 运行正确）。首轮因「编译器源码里没有嵌套先例」而判未实现，属method.md §4.2 警告的「grep 不到 ≠ 不存在」——实际构造探针即通过。
   共同教训：**负例必须先写成可编译的正例形态**，否则错误码指向别处，会把「实现有」误判成「未实现」。
